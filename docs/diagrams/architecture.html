01 · Whole-system overview

Player browsers reach the EC2 application through Cloudflare Tunnel and use Supabase directly, while the server calls external AI and AWS metrics services.

02 · Packages and feature ownership

The shared TypeScript package is imported into React and Node, with multiplayer state on the server and single-player features in the browser.

03 · A multiplayer move

A player sends a reveal request, the authoritative match validates and reveals a cell, and only a completed game's result and replay are persisted.

04 · Sign-in and socket identity

Supabase handles sign-in and configured OAuth, then the game server verifies the current access token and reads the player's profile before accepting account identity.

05 · Accounts, friends and avatars

Supabase users have profiles, optional admin memberships, and friendship relations, while avatar ownership is a storage policy relationship rather than a foreign key.

06 · Matches, seats and ratings

Completed matches contain replay JSON and relate to player result rows, with nullable profile links for guests and winners, while the leaderboard is derived from profiles.

07 · Computer opponents and external APIs

Public board information feeds the solver or local fly circuit; optional Groq and JEV requests assist picks that are checked and played through the normal match rules.

08 · Review coach and hint boundaries

The server loads a completed replay, derives bounded review facts, calls Groq, and validates the answer before returning it to the review UI.

09 · Fruit Fly: offline data and runtime

A one-time neuPrint fetch supplies the connectome circuit, offline games train a readout, and bundled model files power local inference on public board features.

10 · Where data lives

Browser-local preferences and puzzle records are separate from ephemeral multiplayer process state and persistent completed data in Supabase.

11 · Administration and AWS maintenance

Authorized admin sockets receive moderation state and local/service/CloudWatch telemetry, while owner shell maintenance uses Systems Manager independently.

12 · CI, releases and rollback

GitHub CI verifies main, an EC2 timer checks the exact successful push revision, and the deployer builds and switches a release with health-based rollback.

13 · Required two-computer LAN demo

Computer A runs the Node server and its own browser, while Computer B runs only the Vite client and connects directly using the server address in shared source code.

14 · Alternative Vercel + Render setup

The alternative static Vercel client connects to a separate long-lived Render game server and directly to Supabase; it is not part of the EC2 tunnel route.

15 · Database access and permissions

Public browsers can read shared records, signed-in owners can make narrowly permitted personal updates, and the game server alone performs privileged result and moderation operations.
